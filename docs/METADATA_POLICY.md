# Metadata ownership and sidecar policy

## Current behavior

- The original image and any adjacent sidecar are user-owned source data. Import and export do not
  modify or delete either.
- KuroLight extracts a limited set of EXIF values for display, filtering, and filename templates.
  The catalog stores that extracted snapshot per asset. It is not a writable metadata document and
  does not take precedence over a later change to the source file.
- Users can edit a title, description, keywords, and copyright in the Gallery Inspector. These
  values are stored separately as catalog-only overrides: title (256 characters), description
  (5,000), up to 64 keywords (256 characters each), and copyright (512). Keywords are trimmed and
  deduplicated case-insensitively. Overrides do not alter the extracted EXIF snapshot or get merged
  into source metadata.
- Recognized and unrecognized EXIF tags returned by Pillow are stored in `raw_metadata` as strings.
  This preserves values for inspection/catalog survival, not their original binary type, encoding,
  IFD structure, or byte-for-byte representation.
- XMP and IPTC are not merged into or written back to the source image. Existing vendor sidecars are
  left alone unless the user explicitly creates a KuroLight metadata sidecar next to the image.
- KuroLight now supports an explicit adjacent metadata sidecar (`<stem>.kuro.metadata.json`) for
  catalog-only overrides. The sidecar is a structured JSON payload storing the known override field
  set plus any preserved unknown properties. Import/export is opt-in and never modifies the source
  image or a third-party sidecar automatically.
- Exports contain rendered pixels only and strip metadata in every supported format. This includes
  EXIF, XMP, IPTC, and source comments/profiles not explicitly generated by the encoder. The source
  file remains untouched. `strip_metadata` defaults to `true`; requesting metadata preservation
  (`false`) fails explicitly rather than silently dropping metadata.

## Conflict and explicit sidecar policy

Catalog overrides are independent of source metadata and sidecar values, so saving them cannot
conflict with or overwrite either unless the caller explicitly requests a sidecar write. The default
sidecar write behavior raises a conflict error when a known override differs from an existing
KuroLight sidecar; callers may also request `merge` or `overwrite` behavior. Unknown third-party
properties are preserved in the sidecar's `unknown_fields` block and survive round-trips without
being dropped.

Tests verify catalog override validation and persistence separately from extracted EXIF, unchanged
source and sidecar bytes after editing, unknown EXIF values surviving extraction as strings, default
exports containing no source EXIF/XMP, explicit sidecar round-trips with conflict handling, and an
unsupported preserve-metadata request returning an error.
